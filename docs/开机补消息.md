# 开机补消息（睡着时收到的话，用一句话接住）

> 2026-10-20 加。解决的是「晚上关机器人，早上开机，昨晚 @ 她的话一条都没接」。

## 一、为什么原来不接

`wechatauto` 附着微信的瞬间，会把聊天窗口里已有的消息整批回调进来（实测一次约 200 条）。
上游的处理是：这批消息标记 `is_history=True`，**只写进归档、不回复**——否则一开机就会
把昨天的话全回一遍，直接刷屏。

副作用就是：昨晚有人 @ 她，第二天开机她一个字都不说，群里看起来像她睡死了。

## 二、补什么、怎么补

### 触发条件

| 条件 | 说明 |
|---|---|
| 距上次启动 ≥ `min_offline_minutes`（默认 60） | 手动重启两三次不会每次都「刚睡醒」一句 |
| 首次运行（没有状态文件） | 允许补一次 |

> 快速重启**不刷新**计时（只更新 `last_start` 是在真正补过之后），否则一天里连点几次
> 启动按钮就永远凑不满阈值，功能会被饿死。

### 谁能进队列

| 场景 | 收不收 |
|---|---|
| 监控群里 @ 她 / 拍一拍 | 收 |
| 监控群里普通闲聊 | 收（默认 `only_at_me: false`）；`true` 时只收 @ 与拍一拍 |
| 私聊 | 收（`include_private: true`），私聊**一条就接**，不受条数阈值限制 |
| 非监控群 | 不收 |
| 她自己的消息 / `[图片]` `[表情]` `[语音]` 等占位符 | 不收 |
| 当时**在线**已经收过的消息 | 不收（见下面第三层去重） |

### 什么时候才真的说话

- 有人 @ 她 / 拍一拍 / 私聊找她 → **必接**，**不受启动间隔闸门限制**
  （停机期间有人叫她，起来必须应一声，否则就是装死）；
- 群里没人叫她 → 要同时满足「距上次启动 ≥ 60 分钟」和「攒够 `min_messages` 条」；
- 每个会话**只发一句**，不是一条消息回一句。
- 这一次没发出去的（被闸门跳过 / 发送失败）**落盘到 `data/catchup_pending.json`**，
  下次启动接着补，最多留 48 小时。

> 这条规则是 2026-10-20 09:00 补的：当天早上机器人停机 6 分钟，群友在这期间
> `@大肥鱼 打个招呼 / 你好`，08:50 启动时被旧版 60 分钟闸门挡掉，两条消息直接丢了。
> 现在的行为是：@ 无条件必接；其余情况才走闸门，且漏掉的消息会落盘等下次。

## 三、这句话怎么来的

1. 把攒下的消息拼成 `发送者：内容` 的清单（最多 8 条，其余折成「另有 N 条」）；
2. 交给模型，提示词明确要求「用一句话接住，不逐条回答、不编号、不要报表腔」；
3. 输出过一道 `_one_sentence()`：只取第一行、只留第一句、去掉包裹的引号、按 `max_chars` 截断；
4. 模型不可用 / 报错 → 用固定话术（照样是一句，不会退化成逐条回复）。

## 四、三层去重（这是最容易出错的地方）

| 层 | 存在哪 | 挡什么 |
|---|---|---|
| 内容指纹 | `data/catchup_state.json` → `acked` | 同一句话重启两次不重复接（保留 7 天、上限 800 条） |
| 在线已收 | 启动时扫 `data/message_archive.jsonl`（只读末尾 8 MB，跳过 `history` 记录） | 昨晚她在线时已经处理过的消息，不许明天再当「没接住」补一遍 |
| 启动间隔 | `catchup_state.json` → `last_start` | 手动重启不触发 |

## 五、配置（`config.yaml → wechat.catchup`）

| 键 | 默认 | 作用 |
|---|---|---|
| `enabled` | `true` | 总开关；`false` 回到改造前 |
| `only_at_me` | `false` | `true` = 只补 @ 她/拍一拍的 |
| `include_private` | `true` | 私聊要不要补 |
| `min_messages` | `3` | 没人叫她时，群里攒够几条才冒泡 |
| `min_offline_minutes` | `60` | 距上次启动不到这么久就不补 |
| `max_messages` | `40` | 单个会话最多带多少条进提示词 |
| `max_groups` | `3` | 最多补几个会话（按条数从多到少） |
| `max_chars` | `60` | 一句话上限 |
| `delay_after_connect` | `9.0` | 回放窗口（`replay_grace_seconds` 默认 6 秒）之后多久处理 |
| `state_path` | `./data/catchup_state.json` | 去重记账 |
| `pending_path` | `./data/catchup_pending.json` | 没发出去的消息落盘（48 小时） |
| `archive_path` | `./data/message_archive.jsonl` | 「在线已收」索引来源 |
| `skip_seen_live` | `true` | 关闭则连在线收过的也补（不建议） |
| `dry_run` | `false` | `true` 只打日志、不发送（调参用） |

## 六、实测

**2026-10-20 08:40 / 08:42（真机、dry-run）**

- 回放窗口捞到 **40 条**（上限），全部是昨天 17:14 之后她离线期间没人接的话；
- 归档里 **257 条**是当时在线收过的，被第二层去重挡掉；
- 生成的两版一句话（模型不同次）：
  - `刚醒就看到你们在抢会议室蹭吃蹭喝还惦记人家杯子，真是的。`
  - `刚醒就看到谁跟赵老师拜拜了…你们蹭会议室蹭得挺开心啊，杯子吃的就别惦记了。`
- 两次都只发一句；`data/catchup_state.json` 记了 40 个指纹。

**2026-10-20 08:55（真机、真实发送，修复后）**

- 起因：08:44~08:50 停机期间群友发了 `@大肥鱼 打个招呼`、`@大肥鱼 你好`，
  08:50 启动时被旧版 60 分钟闸门挡掉，两条消息丢了；
- 修复后把这两条放进待补队列重启，她在 08:55:38 发了：
  `刚醒就被这么叫，谁是大肥鱼啊，哼。`
- 数据库回读确认：08:55:35 群内出现该条，发送者是她自己的 wxid；待补队列清空。

## 六点五、启动器也修了（这是「不回复」的第一层原因）

当天 08:47 用户点启动，`/api/bot/start` 返回的是 `success:false`（微信窗口当时不可用），
但 `_botctl.ps1` **根本不看返回值**，照样打印「启动指令已发送」，于是机器人一直没起来，
群里怎么 @ 都没人应。

现在 `_botctl.ps1`：

1. 检查 `success`，失败就把 `message` 打出来；
2. 自动重试一次；
3. 成功后继续轮询 `/api/status`，直到 `running=true` 且 `wechat.status=connected`（最多 30 秒）；
4. 仍然失败时打印三条常见原因（微信没登录 / UIA 需热激活 / 旧实例没退干净）并以退出码 1 结束。

## 七、已知边界（别当成 bug）

1. **回放只覆盖「当前打开的聊天窗口」**——微信别的会话昨晚说了什么，她看不到。
   要做全量得切会话，代价太大，没做。
2. **回放只在启动那一次推消息**：同一条消息不会因为再启动一次而重新出现
   （实测 08:52 那次启动完全没有"历史回放"日志）。所以「这次没发出去」必须落盘，
   否则永远补不回来——这就是 `catchup_pending.json` 存在的原因。
3. **本地数据库比 UIA 慢半拍**：实测 08:40 查库，最新只到 08:26（窗口里已经有 08:37 的消息），
   所以这里用 UIA 回放而不是查库。
4. 回放窗口里可能有**更早的旧消息**（不止昨晚），补的时候会一起概括——`min_offline_minutes`
   与「在线已收」两道闸能挡掉大部分，但不能保证 100% 只含昨晚。
5. 私聊默认开：如果私聊很多，会每个私聊都发一句（`max_groups` 限 3 个）。
   觉得吵就 `include_private: false`。
