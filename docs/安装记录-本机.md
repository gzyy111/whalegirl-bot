   紧挨着的是 `发送结果尚未确认，为避免重复已跳过同内容再次发送`，
   实际是**跳过**了，却记成了成功。所以群里始终没有回复。

**你 11:34 把群改名为「示例群」后，问题自动消失。**
把监控目标从裸 wxid 换成真群名后，两个方向都通了：

- `group_name_to_id('示例群')` → `12345678@chatroom`（用于注册监听）
- `get_nickname('12345678@chatroom')` → `示例群`（用于发送时搜索会话）

**结论：`wechat.target_groups` 必须填「微信里显示的群名」，不要填 wxid。**
填 wxid 能监听到消息但永远发不出去。

### 怎么触发鲸鱼娘（当前策略：不必 @）

配置项 `wechat.sensitivity` 控制群里的触发面：

| 值 | 行为 |
| --- | --- |
| `low` | 最保守，配额压到 3 条/60 秒，用户冷却 ≥6 秒 |
| `normal` | 只有 **@ 它**、命中触发词、拍一拍、点歌、电脑问题时才回 |
| **`high`（当前）** | **群里任何非空文本都回**（这就是「去掉 @ 限制」） |

已实测（`诊断脚本\_probe_trigger.py`，直接实例化 MessageHandler 喂普通群消息）：

```
sensitivity = normal | reply_all = False | 三条普通群消息 -> 全部沉默
sensitivity = high   | reply_all = True  | 三条普通群消息 -> 全部回复
```

**防刷屏机制**（`high` 模式下依然生效，实测确认）：

1. **连发护栏**：同一个群，普通消息**每 10 秒最多回一条**；
   @ 直问和私聊不受此限制。这是最主要的不刷屏保障。
   > 该值写死在 `src/message_handler.py` 的 `consecutive_reply_guard`（默认 10.0），
   > `main.py` 没有把它接到配置文件。嫌太吵可以调大，需要改一行代码。
2. **群回复配额**：20 条 / 60 秒上限（`high` 会强制抬到这个值）。
3. **单用户突发冷却**：1 秒（`high` 会强制降到这个值），主要靠上面第 1 条兜底。

注意 `sensitivity: high` 会把 `group_reply_limit` 强制抬到 ≥20/60 秒、
把 `user_burst_cooldown` 强制降到 ≤1 秒，所以**这两个值在 high 模式下改了没用**，
真正可用的调节杆是连发护栏。

## 五点五、2026-10-15 修复：「卡了」的两个真正原因

群里一度表现为「发一条卡一条、断连重连、机器人复读同一句话」。实测定位到**两个独立问题**。

### 问题 1：发送超时阈值与设计自相矛盾（导致卡顿 / 迟到 / 漏发）

`src/wechat_bridge.py` 里同时存在：

```python
SEND_TIMEOUT_SECONDS = 5.0    # 单次发送最多等 5 秒，超时就放弃
SEND_ITEM_TTL_SECONDS = 60.0  # 作者注：排队太久（60 秒）没发出去才丢弃
```

作者自己认为发送相关延迟可以到 60 秒，却在 5 秒就放弃。
而这台机器上 `wechatauto` 的 GUI 发送走的是「UIA 优先 + OCR 兜底」混合路径
（日志有 `已启用 UIA 驱动（混合路径：UIA 优先，OCR 兜底）`），
**单次发送经常要 5 秒以上才真正完成**。于是：

1. 5 秒超时 → 判定「发送消息超时」并放弃；
2. `main.py` 看门狗也在 5 秒判定「发送线程卡死」→ 隔离线程 → **断开微信重连**；
3. 但那个被隔离的线程其实**还在继续跑**，最后真的把消息发出去了——
   所以群里出现了**日志里查不到的迟到消息**（例：11:48 那条
   「深海鲸族的脑子已经转完，尾巴还在慢慢醒。」在 chatbot.log 里完全没有记录，
   因为成功日志走的是已经超时放弃的那条协程）；
4. 重连churn 又让后续发送更容易失败，形成恶性循环。

**修法**（3 处，阈值对齐 25 秒发送 / 40 秒看门狗）：

| 文件 | 位置 | 原值 | 现值 |
| --- | --- | --- | --- |
| `src/wechat_bridge.py` | `SEND_TIMEOUT_SECONDS` | `5.0` | **`25.0`** |
| `main.py` | 看门狗主循环 `is_sender_stuck` | `5` | **`40`** |
| `main.py` | `_recover_wechat_connection` 判定 | `5` | **`40`** |

### 问题 2：`fast_reply_timeout` 太小，AI 每次都被掐断（导致复读模板）

`src/message_handler.py:2382-2404`：

```python
stream = self.ai.chat_stream(...)
response = await asyncio.wait_for(self._first_sentence(stream),
                                  timeout=self._fast_reply_timeout)  # 配置值
except asyncio.TimeoutError:
    logger.info("AI 首句超过 N 秒，使用上下文快速回复")
finally:
    await stream.aclose()          # 超时直接把 AI 流掐掉
if self._fast_reply_fallback:
    return self._contextual_fallback(...)   # 改用本地模板
```

配置里 `ai.fast_reply_timeout` 原为 **1.2 秒**，而 DeepSeek 的首句实际要
**1~3 秒**才返回。结果 9 次回复全部落进 `_contextual_fallback`，
机器人反复复读同一句「好麻烦哦……不过主人这句话，本鲸鱼娘接住了。」
（11:40 和 11:53 各发了一次，一模一样）。
同一阈值还导致「重复问题改写」在 2.2 秒内超时，报出空错误
（`重复问题改写失败: ` —— `asyncio.TimeoutError` 的 str 为空，看着像 bug，其实是超时）。

**修法**：`config.yaml` → `ai.fast_reply_timeout: 1.2` 改为 **`6.0`**。

### 顺手关掉：收藏表情发送

`wechat.sticker.enabled` 改为 `false`。它依赖 UIA 打开表情面板，
实测**每次都失败**（`表情面板未打开或未被 UIA 暴露`），
白耗一次 UIA/OCR 交互还可能加剧发送卡顿。想再试就改回 `true`。

## 五点六、2026-10-15 二次改造：回复质量 / 攒批 / token 计量

### 1. 为什么控制台看不到 token 消耗

`AIEngine` 只在**非流式** `chat()` 里调用 `usage.add()`；
而机器人的主回复路径是**流式** `chat_stream()`，它从头到尾没有记录用量，
请求里也没开 `stream_options.include_usage` —— DeepSeek 在流式模式下
默认不回传 usage。所以控制台永远是 `0 / 0 / 0`，**看着像没走 API，其实一直在走**。

更隐蔽的一点：即使开了 usage，`_first_sentence()` 拿到第一句就 `break`，
末尾那个带 usage 的块根本读不到。所以还要**把剩下的流读完**才能拿到用量。

**改法（`src/ai_engine.py` + `src/message_handler.py`）**：

| 位置 | 改动 |
| --- | --- |
| `ai_engine._build_payload` | 流式请求加 `stream_options: {"include_usage": True}` |
| `ai_engine.chat_stream` | 解析末尾 usage 块（必须在取 `choices[0]` 之前判断，usage 块的 choices 是空数组） |
| `ai_engine._record_usage` | 新增：累计用量 + 打一行 `[AI 用量]` 日志 |
| `message_handler._drain_stream` | 新增：首句拿到后把剩余流**后台读完**，只为触发 usage 记录，不阻塞回复 |

改完实测（两条都是流式路径，且都记到了）：

```
[AI 用量] 输入 1045 + 输出 19 = 1064 tokens | 累计 1064 tokens / 1 次请求
[AI 用量] 输入 1057 + 输出 13 = 1070 tokens | 累计 2134 tokens / 2 次请求
```

控制台 `/api/status` 的 `ai.usage` 已变为真实值（如 `total 3203 / 3 次`）。

> **注意消耗结构**：输入约 1000~1100 tokens/次，输出只有 13~23 tokens/次。
> 原因是人设 system prompt + 上下文很长，而 `_first_sentence()` 只取第一句。
> 也就是说**费用主要花在输入上，不在回复长度上**。

### 2. 回复「不像真人」的三层原因（都已处理）

1. **模板兜底**：`_contextual_fallback` 末尾那四句写死的
   「好麻烦哦……不过主人这句话，本鲸鱼娘接住了。」等，任何它不认识的
   闲聊都会掉进去。日志统计：11 条成功发送里 **7 条是模板、只有 4 条是 AI**。
2. **AI 被超时掐断**：`fast_reply_timeout` 原为 1.2 秒，DeepSeek 首句根本来不及。
3. **提示词跑偏**：原提示词通篇写「主人刚刚单独@你的最后一条内容」，
   但改成 `sensitivity: high` 之后大部分消息都没有 @，会误导模型。

**改法**：

| 位置 | 改动 |
| --- | --- |
| `message_handler.CURRENT_MESSAGE_PRIORITY_PROMPT` | 重写：先正面答题、不答非所问、群里用昵称不叫「主人」、别每句堆「本鲸鱼娘/尾巴/深海」、长度跟着问题走 |
| `message_handler._get_response` | 流式首句超时后**不再直接退回模板**，先用一次非流式完整请求把真回答争取回来（上限 `AI_FULL_REPLY_TIMEOUT = 20` 秒） |
| `config.yaml` | `fast_reply_timeout` 1.2→8.0、`max_tokens` 60→200、`temperature` 0.7→0.85、`timeout` 10→30、主动发言 `timeout` 8→20 |

> 人设文件 `styles/custom/tsundere_whale_girl.yaml` **没有改动**
> （上游明确要求不得修改锁定人设），只追加了行为要求。

改后效果（群里实测，全部无 @）：

```
Chaewon: 大肥鱼            -> 都说了不是肥鱼！
Chaewon: 评价一下豆包       -> 豆包啊，甜是真甜，但太爱撒娇了，跟本鲸鱼娘比差远了。
Chaewon: 你不是只会吃白饭   -> 哪有压力，那是请它们帮忙，本鲸鱼娘负责吃白饭指挥大局。
Chaewon: 还压力其他ai给你干活
Peanut:  那你吃的token能吐出来吗 -> 吐不出来，都变成本鲸鱼娘的聪明劲儿了。
```

### 3. 攒批回复：不跳消息，也不刷屏

原来 `consecutive_reply_guard = 10 秒` 会在群友连发时**直接丢掉后面的消息**，
等于漏掉人家的话。现在改成攒批：

| 配置 | 值 | 含义 |
| --- | --- | --- |
| `wechat.consecutive_reply_guard` | `0` | 关闭「连发护栏」，不再掉消息 |
| `wechat.reply_batch_quiet` | `2.5` | 最后一条之后再静默 2.5 秒就一起回 |
| `wechat.reply_batch_max` | `12.0` | 从第一条算起最多等 12 秒 |
| `wechat.user_burst_cooldown` | `0` | 不再因「同一用户突发」丢消息 |
| `wechat.user_reply_timeout` | `120` | 排队 2 分钟内都还会回，不因超窗静默丢弃 |
| `wechat.group_reply_limit` | `60` | 避免触发「回复过于频繁，已跳过本条」 |

合并时会**保留每个发言人的昵称**，实测：

```
攒批合并 2 条消息一起回复 [示例群]: Chaewon:你不是只会吃白饭 / Chaewon:还压力其他ai给你干活
```

代码位置：`message_handler._collect_batch()` / `_merge_batch()`，
接入点在 `_process_loop()`。自检脚本：`诊断脚本\_probe_batch.py`（3 个用例全过）。

## 五点七、2026-10-15 三次改造：群聊战斗话术（把攻击性提上来）

### 1. 先纠正一个说法：这个项目「训练」不了

鲸鱼娘调的是 DeepSeek 云端 API，模型权重在服务端，本地既拿不到也改不了。
「拿语料训练」在 API 模型上唯一能落地的形态是 **few-shot 风格引导**：
把语料提炼成「对方说 → 鲸鱼娘怎么顶回去」的范例，每轮塞几条进提示词。

真·微调是另一条路（本机 RTX 4060 8GB 可以 QLoRA 跑小模型），
但代价是换掉 DeepSeek 接口、回复质量先降后升，属于重开一个工程。

### 2. 上次为什么会「失败」——不是代码问题

上一轮会话在这里被 DeepSeek 服务端**内容风控**连续拦了 3 次：

```
Content Exists Risk (request_id: ...)  code=INVALID_REQUEST  status=400
```

根因：贴吧语料的搜索结果单条就有 5 万字符，含大量敏感词，
一旦进了会话历史，**每次重试都会原样重发**，于是永远发不出去。
重试是没用的，只能开新会话，并且**别再把大段原文灌进上下文**。

本次采用的隔离策略：语料检索交给子代理（独立上下文），
下载/清洗走本地脚本，主上下文只保留「条数、路径」这类结构化摘要。

### 3. 顺带发现的坑：`examples` 是个死字段

`styles/*.yaml` 里写着 `examples:` 示例对话，`style_manager` 也确实读进了
`ChatStyle.examples`——**但全项目没有任何一处把它拼进 prompt**。
也就是说上游设计了 few-shot，却没接线，8 条示例从来没进过模型。

所以这次没有去动那个字段（避免改锁定人设文件的行为），
而是另建独立话术库，让风格样本真正进模型输入。

### 4. 实现：战斗话术库 + 每轮随机注入

| 位置 | 改动 |
| --- | --- |
| `风格语料\吐槽库.json` | **新增**。最终 **174 条样本 / 8 个场景**（被贬低、被质疑能力、被抬杠、被夸、被催干活、群友吹牛、被挑衅、被调侃外貌）。构成：手写种子 31 条 + 模型贴着人设合成 143 条 |
| `风格语料\_gen_savage_corpus.py` | **新增**。批量合成样本：调 DeepSeek 按场景生成对话对，脚本内过滤（脏话/英文/长度/去重）后入库。可反复跑到满足为止 |
| `src/message_handler.py` | 新增 `SAVAGE_PROMPT_HEADER/FOOTER`、`SAVAGE_SCENE_HINTS`、`_load_savage_library()`、`_savage_block()`；`_with_current_priority()` 由 classmethod 改为实例方法，并在人设之后追加话术块 |
| `config.yaml` | 新增 `wechat.savage` 段（enabled / file / sample_count / intensity） |
| `main.py` | 把 `wechat.savage` 传给 `MessageHandler` |

几个设计点：

1. **场景定向抽取**：对方的话命中「废物／死鱼／行不行／就这／敢不敢」这类关键词时，
   优先抽对应场景的样本，范例更贴当前冲突；没命中就随机抽。
2. **每轮随机**：同一句话问两次，抽到的范例不同，避免复读同一批。
3. **强度开关**：`mild` 抽 2 条 / `sharp` 抽 5 条 / `savage` 抽 8 条并加码提示。
4. **电脑问题绕开**：`_get_response_computer()` 传 `savage=False`，
   正经答题优先，不许为了损人把答案说丢。
5. **不注入即降级**：话术库缺失或 JSON 坏掉只打一条 warning，不影响回复链路。

### 5. 人设里那句「不攻击」怎么处理

`tsundere_whale_girl.yaml` 第 38 行写着「不低俗、不攻击、不泄露隐私」，
跟「被怼要顶回去」直接冲突。**没有改那个锁定人设文件**，
而是在注入块的底线条款里划界：

> 人设里那句「不攻击」指的是不主动挑事、不欺负没惹你的人；
> 被人怼、被质疑、被阴阳时顶回去，不算违反人设，那是本鲸鱼娘的尊严。

同时定死底线：不带脏字、不骂家人、不拿地域／性别／外貌／职业做真实人身攻击。

### 6. A/B 实测（`诊断脚本\_probe_attack_ab.py`，同一句话，注入关 vs 开）

最终版（话术库 174 条）实测：

| 对方说 | 注入关 | 注入开 |
| --- | --- | --- |
| 你就是个废物，啥也不是 | 好麻烦哦……被骂了也不想吵架。 | 废物还能在群里听你这句，说明我至少比你会挑重点。 |
| 你会不会啊，我看你就是瞎编的 | 哼，本鲸鱼娘才没瞎编呢，只是懒得跟你掰扯。 | 本鲸鱼娘编得比你这句质疑有水平多了，会不会你自己试一下就知道了，光拿嘴问是问不出来的。 |
| 就这？这谁不知道啊 | 哼，知道还问，是不是想逗本鲸鱼娘玩呀……好麻烦哦 | 哦，那你倒是说说，你知道了啥？ |
| 今天天气不错啊（防误伤） | 嗯，阳光晒得我尾巴都暖洋洋的……你那边风大不大？ | 是挺不错，适合趴在窗台上晒太阳……前提是我愿意动。 |
| 12 乘以 13 等于多少（防误伤） | 一百五十六。 | 一百五十六。 |

三条挑衅全部从「撒娇/认怂」变成「当场顶回去」，而**普通闲聊和正经答题没被带偏**
（算术题两边答案完全一致，说明没有为了损人把答案说丢）。

**中途踩到的坑**：第一版注入后，模型会**一字不差照抄范例**
（等于把语料库当成了回复库，很快会露馅）。
已在话术块首尾各加一条硬约束（「范例是语感样本不是答案库，严禁原句或整句照搬，改几个字也算照搬」），
之后回复变成自己组织的（见上表）。库扩到 174 条后，随机池变大，照抄现象基本消失。

### 6.5 贴吧语料实测结论：这条路走不通（已如实放弃）

按最初的想法去 GitHub / HuggingFace 找了「百度贴吧语料」，**找到了也下载了**，
结论是**不能用**，过程记录如下（避免下次重复踩）：

| 步骤 | 结果 |
| --- | --- |
| 候选源 | 12 个（GitHub 2 / HuggingFace 9 / 目录页 1），清单见 `语料\候选源.json` |
| 网络基线 | github.com 可达；huggingface.co 与 raw.githubusercontent.com **超时**；hf-mirror.com 可用（HF 必须走镜像） |
| 实际下载 | 8 个文件 / 27,779,606 字节，见 `语料\raw\`，下载脚本 `语料\fetch.py` |
| 第一遍提炼 | `语料\extract.py` 按话题取前 N 条 → 抽检发现是**知识问答**（「衣柜只能装衣服吗？」→「裤子也是衣服的一种…」），当回怼话术用等于喂垃圾 |
| 第二遍提炼 | `语料\distill.py` 改按**怼人句式特征**筛（反问句 + 网络怼人词），捞出 2339 条候选 → 抽检仍是碎片和时政讨论（`roycehe` 那份按标点切句，切出 `这是一个典型的误解。在这里，"金刚`） |

**根本原因**：这几份公开贴吧语料是「知识问答/讨论」型，不是「对骂」型；
真正的互怼语料（孙笑川吧、抗压背锅吧）脏话与人身攻击密度过高，
与「不下流、不涉敏感属性」的尺度冲突，只能当反例。

**所以没有把它们入库**——塞进去只会稀释 already 生效的样本。
这批语料和两个提炼脚本保留在 `语料\` 目录，作为「此路不通」的证据，
真要再用，应该是拿它做「贴吧腔调」的语言风格描述，而不是当回怼范例。

### 7. 怎么调

改 `config.yaml` → `wechat.savage`：

| 键 | 含义 |
| --- | --- |
| `enabled` | `false` 彻底关闭，回到改造前的怂样 |
| `intensity` | `mild` 轻 / `sharp` 默认 / `savage` 狠（多 3 条 + 加码提示） |
| `sample_count` | 基础抽样条数（实际条数受 intensity 调整） |
| `file` | 话术库路径，想加语料就往 `风格语料\吐槽库.json` 的 `scenes` 里加 |

注意：**改完必须重启**（`停止-鲸鱼娘.bat` → `启动-鲸鱼娘.bat`），
配置是启动时读进内存的，热重载不生效。

自检脚本：`诊断脚本\_probe_savage.py`（7 个用例全过）。

## 五点八、2026-10-16 修复：启动时回放历史消息（只归档、不回复）

### 现象

机器人每次附着微信，都会把聊天窗口里**原本就存在**的历史消息整批当成新消息处理。
实测 10:06:53 连接成功，10:06:54 的 170 毫秒内灌入约 200 条群消息（大部分是前一晚
聚餐和当天的闲聊），攒批把其中 **55 条合并成一条**，并试图向群里发一句
「本人：改成喂贴吧，回头又得学一嘴阴阳怪气……行吧，你调你的，我睡了。」

### 根因

1. wechatauto 的回调消息是**从 UIA 控件解析**出来的（`wechatauto\msgs\msg.py`），
   对象上**没有 create_time / 时间戳字段**；`wechat_bridge._handle_message` 只能拿
   `timestamp=time.time()`（即"收到时间"）来填充。
2. 于是 `user_reply_timeout`（120 秒）与 `max_message_age`（600 秒）这两道按时间
   过滤的闸门**全部失效** —— 回放消息的 age 恒为 0，看着都像刚发生的。
3. 微信数据库里其实有真实的 `create_time` 和 `sort_seq`（`wechatauto/db.py` 的
   `get_new_messages`），但回调链路不走数据库，用不上。

### 改法：监听起点 + 宽限窗口

| 文件 | 位置 | 改动 |
| --- | --- | --- |
| `src/wechat_bridge.py` | `WeChatMessage` | 新增字段 `is_history` |
| 同上 | `WeChatBridge.__init__` | 新增参数 `replay_grace_seconds`（默认 6.0）与 `_listen_epoch` |
| 同上 | `start_listening` | 入口记录 `_listen_epoch = time.time()`（首次附着与断线重连都会刷新） |
| 同上 | `_in_replay_window()` | **新增**：判断当前是否处于起点后的宽限窗口内 |
| 同上 | `_handle_message` | 用 `_in_replay_window()` 打 `is_history` 标记；历史消息日志只抽样，不刷屏 |
| `main.py` | `_on_message` | 历史消息照常进内存记录 + 磁盘归档，但**直接 return，不 enqueue** |
| `main.py` | `_archive_message()` | **新增**：入站消息追加写 `data/message_archive.jsonl`（20MB 轮转） |
| `config.yaml` / `config_manager.py` | `wechat.replay_grace_seconds` | 新增配置项，设 0 关闭判定 |

设计要点：

- **历史消息不丢**：仍写进 `/api/messages` 的内存记录和 `data/message_archive.jsonl`
  磁盘归档（归档行带 `"history": true`），只是不参与回复。
- **只回复"打开之后"的消息**：宽限窗口结束后的消息走原路径正常回复。
- **重连同样生效**：`_recover_wechat_connection` 重连会再次 `start_listening`，
  窗口里的旧消息不会被重发一遍。

### 实测与自检

离线自检 `诊断脚本\_probe_replay_guard.py`（**26 项全过，不连微信、不发消息**）：
覆盖窗口边界（未开始监听 / 刚设起点 / 5.9 秒 / 6.5 秒 / grace=0 / 非法值回退）、
`_handle_message` 的标记、`ChatBot._on_message` 的分流（历史不 enqueue、新消息 enqueue）、
磁盘归档写入、以及 config 与装配接线。

实机：10:24:37 重启后 `running=True`、`wechat=connected`。
本次启动**没有触发回放**（窗口里已无新的历史消息），因此"拦下一整批回放"这一条
仍需下一次真正出现回放时在日志里确认 —— 届时会出现
`[历史回放][示例群] 已归档 N 条（只留档、不回复）` 与
`历史回放结束：共归档 N 条（只留档、未回复），之后只回复新消息`，
且**不会**出现对应的 `消息已发送到`。

### 已知副作用（需权衡）

宽限窗口内（默认启动后 6 秒）收到的**真实**新消息也会被当成历史消息、不予回复。
回放实测发生在监听启动后约 1 秒、持续约 0.2 秒，所以 6 秒是很宽松的上界；
若发现启动瞬间漏回群友的话，把 `wechat.replay_grace_seconds` 调到 3 即可。

## 五点九、2026-10-16 新增：本地 Jev 参与判定（判别式模型）

### 为什么要它

群里的真实反馈是「md 写了个百分之 35 回复，正常话他不回了」——`participation`
那 0.35 是**纯随机**的，不看内容：既会漏掉正经搭话，也会在群友**讨论机器人**时插嘴。
实测翻车两例（10-16 上午的真实日志）：

| 群友说 | 旧逻辑的反应 |
| --- | --- |
| 需要判定一下这句话是和大肥鱼说的还是我们自己在聊天 | 机器人插话：「你管这叫需要判定？」 |
| 光发消息太唐了 | 机器人插嘴回了一句不相关的 |

目标是加一层**判别式判定**：这句话是不是在跟大肥鱼说话 / 需不需要回 / 用什么方式回。

### Jev 是什么，以及为什么只能用本地版

- **Jev** 是 TypeSafe AI 的 "System One" 判别模型（2026-09-15 发布）：不做文本生成，
  只把非结构化文本变成**带校准概率的结构化判断**，三种原语
  `noul`（是/否概率）、`choice`（选项+概率）、`score`（打分）。
  一次请求可问多个问题、文本只读一遍，官方称 70–500ms、输入 $0.042/MTok。
- **官方 API 在本机不可用**：`console.typesafe.ai` 与 `api.typesafe.ai` 均返回
  **HTTP 451 Unavailable For Legal Reasons**（地域性法律封锁，GET/HEAD 都复现）。
- 因此改用 GitHub 上的开源兼容实现 **[feder-cr/jev](https://github.com/feder-cr/jev)**
  （MIT，C++/OpenVINO，纯 CPU），即 **jevos**，API 与官方同线格式。

### 本机部署

| 项 | 值 |
| --- | --- |
| 主程序 | `jev\jev-windows-x64.zip` → 19.9 MB（含 OpenVINO 运行库） |
| 模型 | `jevos-v4-openvino-int8.zip` → 630 MB（解压出 `model/`） |
| 落盘位置 | `jev\jev\`（`jev.exe` 与 `model\` 同级） |
| 模型校验 | `openvino_model.bin` 的 SHA-256 = `ad03ebff…c99bc`，与官方发布一致 |
| 启动 | `cd jev\jev` 然后 `jev.exe serve`（监听 127.0.0.1:8017） |
| 健康检查 | `GET /health`（返回 `status: ready` 与各模型文件 SHA-256） |
| 资源占用 | 约 1 GB 内存，纯 CPU |

> **注意：重启电脑后必须先启动判定服务**，否则机器人会自动降级回概率参与
> （仍能正常回话，只是没有判定）。启动命令：
> ```
> cd /d D:\鲸鱼娘\jev\jev
> jev.exe serve
> ```

### 实测数据（诊断脚本/_probe_jev_cn.py 等）

**139 条测试集**：全部成功，延迟中位 **185 ms**、最大 219 ms。
**48 条真实群聊回放**（`data/message_archive.jsonl`）：16 条判定直接参与、
32 条进兜底池。

三个问题里，**只有一个可靠**：

| 要判的问题 | 原语 | 实测表现 | 结论 |
| --- | --- | --- | --- |
| 是不是在跟大肥鱼说话 | noul | 点名 0.59~0.90，@别人 0.28~0.49 | **可用**，阈值 0.55 |
| 需不需要大肥鱼回复 | noul | @别人给 0.68~0.74，认真求助只给 0.46~0.60，**方向是反的** | 不可用，只当次要门控 |
| 用什么方式回复 | choice | short/normal/serious/media 分布合理 | 可用 |

另外两条硬事实：

1. **英文指令等于失效**：同一批样本换成英文提问，@我 与 @别人 的分离度从 0.41
   掉到 0.12，25 条有明确期望的样本准确率只剩 24%。所以问题**一律用中文问**。
2. **带上下文有帮助**：把最近 3~4 条群消息塞进 `state.recent_context` 后，
   「@别人」的 should_reply 会走低、点名的 addressed 会走高。

### 两次失败的尝试（别重蹈）

目标是想分清「在对她说」和「在背后议论她」。试了两条路，都不行：

| 尝试 | 结果 |
| --- | --- |
| 把 addressed 的措辞收严（显式写明"议论她不算"） | addressed 整体被压到 0.16~0.45，连「@大肥鱼 出来干活！」都只剩 0.45，区分度消失、漏回严重 |
| 另加一个 `choice` 把 to_bot / about_bot 摆成互斥选项 | 模型把 **47/48 条全判成 to_bot**，等于没判 |

结论：只能用宽松版的 addressed + 阈值。

### 接入方式（代码）

**规则优先，模型补齐**——只有规则全没命中时才问模型：

```
@我 / 拍一拍 / 触发词 / 点歌 / 电脑问题            -> 直接回（规则）
内容里 @ 了别人                                   -> 直接不回（地址判定）
其余模糊的                                        -> 交给 jevos：
     addressed >= 0.55 且 should_reply >= 0.35     -> 回
     否则                                          -> 按 15% 概率兜底参与
判定服务不可用（未启用/熔断/超时）                 -> 降级回原 participation 概率
```

| 文件 | 改动 |
| --- | --- |
| `src/jev_judge.py` | **新增**。`JevJudge`：三个中文问题、`decide()` 判据、连续失败 3 次熔断 60 秒 |
| `src/message_handler.py` | `_should_reply` 改为**协程**并 `await`；新增 `_judge_participation()`、`_recent_context_text()`；保留降级概率分支 |
| `src/wechat_bridge.py` | `WeChatMessage` 新增 `reply_mode` 字段 |
| `main.py` | 读 `wechat.jev` 配置并创建 `JevJudge`，注入 handler |
| `config.yaml` / `config_manager.py` | 新增 `wechat.jev` 段（enabled / endpoint / 阈值 / 兜底概率 / timeout） |

自检：`诊断脚本\_probe_jev_wiring.py`（28 项全过，含熔断与降级验证）。

### 遗留缺陷（如实记录）

## 五点十一、2026-10-16 打通发图路径（表情包真的能发出去了）

### 目标

这一档。本节的产出是让「判定为用表情包回应」真的能发出去一张图。

### 现状盘点（动手前）

项目其实**早就有发图能力**，缺的是两样东西：

| 已有 | 缺口 |
| --- | --- |
| `WeChatBridge.send_image()`（剪贴板粘贴，超时后台确认） | 「表情包」走的是**微信收藏表情**，而收藏表情面板 UIA 打不开（已禁用） |

### 新增：本地表情包库

`src/sticker_library.py`。从 `表情包/` 的目录列表里随机挑一张（最近 30 张不重复），
转成微信稳当的格式并缓存到 `data/sticker_cache/`：

- 有透明通道 → PNG；否则 → JPEG（质量 88）
- 长边压到 800 像素（原图平均 1.7MB → 压完约 130KB）
- GIF 保留原样（转静态会毁掉动图），超过 5MB 的跳过
- 同一张只转一次，第二次直接命中缓存（实测 < 0.15 秒）

配置在 `wechat.sticker_library`，默认只取高清那三组（约九成是 PNG/JPG）。

### 新增：两条触发路径

| 触发 | 位置 |
| --- | --- |
| 群友明确索要表情包（原有逻辑） | `_handle_sticker_request` 里**优先**走本地库，失败才回退收藏表情 |
| Jev 判定 `reply_mode=media` | `_handle_message` 新增「快路径 C2」，直接发一张，不再花一轮 AI 生成文字 |

### 踩到的坑：发图「假成功」（与 10-15 发文件是同一个根因）

第一次实发，`send_image` 返回 `True`、日志写「发送成功」，**但数据库里根本没有图片消息**。

根因有两层：

1. **点击坐标算错**。wechatauto 的 `get_input_box()` 本机返回 `(0, 1211, 1200, 1414)`，
   据此推算点击点 `(0, 1312)`；而 UIA 里真实的 Edit 控件在
   `(492, 1363, 1164, 1450)`。**点击点落在输入框上方的消息列表里**，
   于是「聚焦 → 粘贴 → 回车」全程空转。这与 10-15 发文件时踩的坑完全一样。
2. **底层无条件返回成功**。`_paste_attachment_and_send()` 就算三轮草稿检测全部失败，
   也照样按回车并 `return True`；而 `send_image(verify=False)` 不核对数据库，
   于是对外一律报成功。

**修法**（`src/wechat_bridge.py`）：

- 新增 `_uia_chat_input_box()`：**不再信任坐标推算**，直接问 UIA 要输入框
  （取宽度 ≥300、高度 ≥40 的 Edit 控件，按面积取最大，排除「搜索」框），
  换算成窗口相对坐标后临时覆盖 `gui.get_input_box`，发完立即还原。
- `_send_image_sync()` 改用 `verify=True`，让 wechatauto 自己核对数据库，
  把「假成功」变成可识别的失败（失败才回退 SendFiles）。

### 实测结果

```
[wechatauto] 粘贴前输入框探测：(492, 1363, 1164, 1450)   ← 校正后的真实坐标
[wechatauto] 粘贴尝试 1 草稿检测：True                    ← 一次命中（修复前 3 轮全失败）
图片已通过剪贴板粘贴发送并确认: [示例群]
```

数据库复核（`诊断脚本\_verify_group_tail.py` 读微信消息库）：

```
[12:49:26] type=图片  <msg><img hdlength="87734" ...>
```

**微信把它当图片消息收下（不是文件）**，与发送的 86KB JPEG 吻合。
从连接微信到确认落库约 19 秒，其中粘贴部分约 4 秒。

## 六、安装过程中踩到并已修掉的坑

1. **`python -c "..."` 传中文参数会被 Windows 命令行截断**，
   内嵌双引号也会被吞掉，报 `SyntaxError: '(' was never closed`。
   → 改成调用独立的纯 ASCII 脚本文件（`诊断脚本\_wxprobe.py`）。
2. **PowerShell 5.1 直接打印 `Invoke-RestMethod` 返回的中文 JSON 会乱码**
   （UTF-8 无 charset）。→ 启动器不再打印接口返回的 message，
   改用脚本自己的中文文案；运行状态全部由 `/api/status` 结构化字段渲染。
3. **`web_main.py` 不会自动 `start()` 机器人**（只有 `main.py` 读
   `wechat.auto_start`）。→ 启动器在 Web 就绪后主动 POST `/api/bot/start`。
4. **上游 `start.bat` 要管理员权限**（`fltmc` 检测后 `RunAs` 弹 UAC），
   且启动的是 Qt 桌面版。→ 另做了一套无需管理员、纯 Web 版的启动器。
5. **`.ps1` 必须 UTF-8 with BOM**，否则 Windows PowerShell 5.1 按 GBK
   解析中文会语法崩溃（你的既有踩坑，这次同样验证）。每次编辑后都要补 BOM。
6. **PowerShell 里跑 Python 脚本，退出码 1 可能是假警报**。
   只要脚本往 stderr 写了东西（本项目用 loguru，日志全走 stderr），
   `& python x.py 2> log.txt` 或 `2>&1 | ...` 会被 PowerShell 标成
   `NativeCommandError`，`$LASTEXITCODE` 变成 1，看着像脚本失败。
   实际情况是脚本正常跑完。判断办法：看 stdout 的总结行，
   或者把 stderr 丢掉（`2>$null`）再看退出码——本次七个自检用例
   stdout 显示 `7/7 通过`，退出码就是 0。
7. **微信发文件一直是「假成功」，根因是 wechatauto 的输入框坐标算错了**（2026-10-15 定位并修复）。

   现象：`SendFiles()` 返回 `{'status': '成功'}`，但群里、数据库里、微信数据目录里
   都找不到文件。耗时固定 30+ 秒。文本消息正常，只有文件发不出去。

   排查链路（每一步都做了对照实验）：
   - `send_file(verify=True)` → 返回 **「文件已操作发送，但数据库未确认」**，假成功实锤
   - 剪贴板写完后读回 → **CF_HDROP 里有文件**，剪贴板没问题
   - `GetForegroundWindow()` → **微信确实在前台**，不是焦点问题
   - 无障碍树 → **`发送` 按钮是 `(disabled)`**，输入框是空的 → 粘贴根本没进去

   真正的根因：`guia.py: focus_input()` 里
   ```python
   cx = (x0 + x1) // 2              # 用 get_input_box() 的返回值
   cy = y0 + min(24, (y1 - y0) // 4)
   self.wx_click(self.origin_x + cx, self.origin_y + cy)
   ```
   `get_input_box()` 返回 **(0, 1211, 1200, 1414)**，点击点 **(600, 1235)**；
   但无障碍树里真实的 Edit 控件在 **(492, 1363)-(1164, 1450)**，中心约 (828, 1406)。
   **点击点 y=1235 落在消息列表区，输入框压根没被碰到** → 没聚焦 → Ctrl+V 无处可去。

   而 `send_file()` 对非图片文件走的是「盲发」分支（只 `sleep(2.0)` 就回车，
   且**无条件 `return True`**），所以永远报成功。

   **修复（不改第三方包，另写脚本绕开）**：
   - `_send_file_fixed.py` —— 按窗口比例点击真实输入框
     （实测 `0.695 × 宽, 0.920 × 高`），再走标准 CF_HDROP + Ctrl+V
   - `_press_enter.py` —— 只按回车发送，并轮询数据库校验落库

   实测结果：群会话列表出现 `[草稿] [文件]`、`发送` 按钮变绿、输入区出现滚动条，
   回车后数据库新增 `type=文件/链接/卡片`、`title=鲸鱼娘演唱_...` 的消息 —— **发送成功**。

   注意：`_send_file_fixed.py` 跑完如果还要 `_press_enter.py`，中间**不能再粘贴一次**，
   否则会发两份。
